# Go GMP 调度模型深度解析

> 本文档深入讲解 Go 语言的 GMP 调度模型，从核心概念到实际应用场景，结合费曼学习法帮助理解。

## 0. 阅读前先建立一个心智模型

GMP 最容易被讲复杂。可以先用一个工厂类比建立直觉：

```text
┌─────────────────────────────────────────────────────────────┐
│                      GMP 工厂类比                            │
├─────────────────────────────────────────────────────────────┤
│  G：任务卡片                                                 │
│     记录“要执行哪段代码、执行到哪里、栈在哪里”                │
│                                                             │
│  M：工人                                                     │
│     真正干活的人，对应 OS 线程                               │
│                                                             │
│  P：工作台                                                   │
│     工人必须站在工作台前才能执行 Go 代码；工作台上有任务队列  │
│                                                             │
│  调度器：车间主管                                             │
│     决定工人从哪个工作台拿任务、空闲时去哪里偷任务            │
└─────────────────────────────────────────────────────────────┘
```

关键点：**G 不是线程，M 才是线程；P 也不是 CPU，而是 Go runtime 掌握的一份执行许可和本地资源。**

## 1. 概述与背景

Go 语言的并发模型建立在 **GMP** 三个核心组件之上。GMP 模型的设计目标是：

- **高并发**：支持百万级 goroutine 并发执行
- **低开销**：goroutine 创建和切换代价极低（~2KB 栈 vs OS 线程 ~1-8MB）
- **高效利用多核**：通过 `GOMAXPROCS` 个 P 限制同一时刻执行 Go 代码的并行度，并用本地队列降低调度锁竞争

```text
┌─────────────────────────────────────────────────────────────┐
│                    GMP 模型核心目标                          │
├─────────────────────────────────────────────────────────────┤
│  传统线程模型：                                               │
│    1:1 映射 ──► OS 线程 ──► 上下文切换代价高                  │
│    线程数受限于 OS 资源                                       │
│                                                             │
│  GMP 模型：                                                  │
│    M:N 映射 ──► goroutine 复用 OS 线程                       │
│    数十万 G 可以在少量 M 上高效调度                           │
└─────────────────────────────────────────────────────────────┘
```

## 2. 核心组件详解

### 2.1 G (Goroutine)

**G** 是 Go 程序中最基本的执行单元，可以理解为"轻量级线程"。

```go
// runtime/runtime2.go
type g struct {
    stack       stack       // goroutine 的栈空间
    stackguard0 uintptr     // 栈增长保护
    m           *m          // 绑定的 M（运行时）
    sched       gobuf       // 保存的执行状态（PC、SP）
    goid        int64       // goroutine ID
    waitsreason waitReason  // 等待原因
    // ...
}
```

**关键特性**：

| 特性 | 说明 |
|------|------|
| 栈大小 | 初始 2KB，可动态增长到 1GB |
| 创建代价 | 极低，只需分配栈空间和 g 结构体 |
| 切换代价 | 用户态切换，无需系统调用 |
| 数量限制 | 没有固定语言级上限，实际受内存、调度压力和业务泄漏约束 |

### 2.2 M (Machine)

**M** 代表 OS 线程，是实际执行代码的实体。

```go
// runtime/runtime2.go
type m struct {
    g0      *g      // 特殊的 goroutine，用于执行调度代码
    curg    *g      // 当前正在运行的 goroutine
    p       puintptr // 绑定的 P
    nextp   puintptr // 下一个要绑定的 P
    oldp    puintptr // 之前的 P（用于 handoff）
    // ...
}
```

**关键特性**：

- M 的数量可以超过 P：阻塞系统调用、cgo、runtime 需要额外线程时会创建或唤醒更多 M
- M 在找不到可运行的 G 时可能 park（休眠），等待被调度器唤醒
- M 进入阻塞系统调用时，P 可能被摘下并交给其他 M（handoff），避免 P 的本地队列一起“卡死”

### 2.3 P (Processor)

**P** 是逻辑处理器，代表执行 Go 代码所需的资源。P 的数量等于 `GOMAXPROCS`。

```go
// runtime/runtime2.go
type p struct {
    id          int32
    status      uint32
    m           *m          // 绑定的 M
    runqhead    uint32      // 本地队列头
    runqtail    uint32      // 本地队列尾
    runq        [256]guintptr // 本地运行队列（环形队列）
    runnext     guintptr    // 下一个要执行的 G（优先）
    // ...
}
```

**关键特性**：

```text
┌─────────────────────────────────────────────────────────────┐
│                      P 的核心作用                           │
├─────────────────────────────────────────────────────────────┤
│  1. 资源隔离：每个 P 有自己的本地运行队列                    │
│  2. 减少锁竞争：G 优先在本地队列调度，无需全局锁             │
│  3. 局部性：本地队列和缓存减少跨线程/全局锁竞争              │
│  4. 限制并发度：GOMAXPROCS 决定同时执行的 goroutine 数       │
└─────────────────────────────────────────────────────────────┘
```

## 3. 调度机制

### 3.1 整体调度流程

```text
┌─────────────────────────────────────────────────────────────┐
│                      M 调度循环                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ┌─────────────────────────────────────────────────────┐   │
│   │                    schedule()                        │   │
│   └─────────────────────────────────────────────────────┘   │
│                          │                                  │
│          ┌───────────────┼───────────────┐                  │
│          ▼               ▼               ▼                  │
│   ┌─────────────┐ ┌─────────────┐ ┌─────────────┐          │
│   │ 本地队列    │ │ 全局队列    │ │ 网络轮询    │          │
│   │ (P.runq)    │ │ (global)    │ │ (netpoll)   │          │
│   └─────────────┘ └─────────────┘ └─────────────┘          │
│          │               │               │                  │
│          └───────────────┼───────────────┘                  │
│                          ▼                                  │
│                  ┌─────────────┐                            │
│                  │ 找到 G      │                            │
│                  └─────────────┘                            │
│                          │                                  │
│                          ▼                                  │
│                  ┌─────────────┐                            │
│                  │ execute(G)  │                            │
│                  └─────────────┘                            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 调度策略

Go 调度器采用多种策略来保证公平性和高效性：

#### 3.2.1 本地队列优先

```text
P.runq (本地运行队列，环形队列，容量 256)
┌─────────────────────────────────────────────────────────────┐
│  runqhead ──► G1 ──► G2 ──► G3 ──► ... ──► Gn ──► runqtail  │
│              │                                   │          │
│              └───────────────────────────────────┘          │
│                      环形队列                               │
└─────────────────────────────────────────────────────────────┘

简化后的取 G 顺序：
1. `runnext`（优先级最高，通常用于继承时间片/保持局部性）
2. 本地队列（`P.runq`，无锁或低锁竞争路径）
3. 全局队列（调度器会周期性检查，避免全局队列饥饿；常见实现细节是每 61 次调度检查一次）
4. 网络轮询（非阻塞 I/O 就绪的 G）
5. work stealing（从其他 P 偷取）
```

> 注意：这是便于理解的主路径，不等价于 `runtime.schedule` / `runtime.findRunnable` 的完整源码分支。真实实现还要处理 GC、trace、timer、spinning M、stop-the-world 等运行时事件。

#### 3.2.2 Work Stealing

当 P 的本地队列为空时，会尝试从其他 P 偷取一半的 G：

```text
┌─────────────────────────────────────────────────────────────┐
│                    Work Stealing 机制                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  P0 (空闲)                    P1 (繁忙)                      │
│  ┌─────────────┐              ┌─────────────┐               │
│  │ runq: []    │              │ runq: [G1..G10]             │
│  └─────────────┘              └─────────────┘               │
│        │                            │                       │
│        │    ┌───────────────────────┘                       │
│        │    │ 偷取一半 (5 个 G)                              │
│        ▼    ▼                                               │
│  ┌─────────────┐              ┌─────────────┐               │
│  │ runq: [G6..G10]           │ runq: [G1..G5]              │
│  └─────────────┘              └─────────────┘               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

```text
│      │           │              │       │                    │

```

## 4. Channel 阻塞机制深度解析

### 4.0 Channel 阻塞与系统调用阻塞的区别

很多资料会把“goroutine 阻塞”统一描述成“释放 P”。这个说法不够准确，需要区分两类阻塞：

| 场景 | G 状态 | M 是否阻塞 | P 是否需要 handoff | 典型机制 |
|------|--------|------------|--------------------|----------|
| channel / mutex / cond 等 runtime 可管理阻塞 | `_Gwaiting` | 不阻塞 OS 线程 | 通常不需要；M 继续持有 P 去调度其他 G | `gopark` |
| 阻塞系统调用 | `_Gsyscall` | M 阻塞在内核 | 可能需要；P 交给其他 M | `entersyscall` / `handoffp` |
| 网络 I/O | `_Gwaiting` | M 不阻塞在 socket 上 | 通常不需要 | netpoller |

所以，`ch <- 1` 没有接收方时，阻塞的是 **G**，不是 **M**；M 会切回调度器继续运行其他 G。

### 4.1 无缓冲 Channel 发送阻塞

当执行 `ch <- 1` 且没有接收方时：

```text
┌─────────────────────────────────────────────────────────────┐
│                  无缓冲 Channel 发送流程                     │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. runtime.chansend(c, &1, block=true)                      │
│     │                                                       │
│     ├─ 检查 recvq：是否有接收方在等待？                     │
│     │   └─ 否                                               │
│     │                                                       │
│     ├─ 检查 buf：是否有缓冲空间？                           │
│     │   └─ 否（无缓冲 channel，dataqsiz=0）                 │
│     │                                                       │
│     └─ 进入阻塞路径                                         │
│                                                             │
│  2. acquireSudog()                                           │
│     └─ 获取一个 sudog 结构体                                │
│                                                             │
│  3. 初始化 sudog                                             │
│     mysudog.g = G_A                                          │
│     mysudog.elem = &1  ──► 指向要发送的值                    │
│     mysudog.c = ch                                           │
│                                                             │
│  4. c.sendq.enqueue(mysudog)                                 │
│     └─ 将 sudog 放入发送等待队列                            │
│                                                             │
│  5. gopark(chanParkCommit, &c.lock, waitReasonChanSend)      │
│     ├─ G_A: _Grunning ──► _Gwaiting                        │
│     ├─ M0 切到 g0 栈，继续持有 P0                           │
│     └─ M0 进入 schedule()，用 P0 寻找其他可运行 G            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 sudog 结构详解

`sudog` 是 G 在等待队列中的"身份证"，携带等待所需的所有上下文：

```go
// runtime/runtime2.go
type sudog struct {
    g     *g              // 指向等待的 goroutine
    elem  unsafe.Pointer  // 数据元素指针
    c     *hchan          // 等待的 channel
    next  *sudog          // 队列中的下一个
    prev  *sudog          // 队列中的上一个
    // ...
}
```

**为什么需要 sudog 而不只是 *g？**

```text
┌─────────────────────────────────────────────────────────────┐
│                   sudog 的设计意图                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  1. 数据关联：                                               │
│     sudog.elem 可以指向要发送/接收的数据                     │
│     └─ 实现直接拷贝，避免经过 channel buffer 二次中转         │
│                                                             │
│  2. Channel 关联：                                           │
│     sudog.c 记录等待的是哪个 channel                        │
│     └─ 唤醒时知道是哪个 channel 触发的                      │
│                                                             │
│  3. 队列操作：                                               │
│     next/prev 支持双向链表的 O(1) 插入删除                   │
│     └─ 高效的队列管理                                        │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 唤醒机制：直接拷贝

当接收方出现时，会发生**直接拷贝**（direct copy）：

```text
┌─────────────────────────────────────────────────────────────┐
│                    直接拷贝机制                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  G_A (发送方)                    G_B (接收方)                │
│  ch <- 1                         result := <-ch             │
│      │                               │                      │
│      ▼                               ▼                      │
│  ┌─────────────────────────────────────────────────────┐    │
│  │               runtime.chanrecv                       │    │
│  └─────────────────────────────────────────────────────┘    │
│                          │                                  │
│                          ▼                                  │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  1. sg := c.sendq.dequeue()                          │    │
│  │     └─ 取出 G_A 的 sudog                            │    │
│  │                                                      │    │
│  │  2. recvDirect(c.elemtype, sg, &result)              │    │
│  │     └─ 直接从 sudog.elem 拷贝数据到 result          │    │
│  │         └─ 不经过 channel buffer 的中转              │    │
│  │                                                      │    │
│  │  3. goready(sg.g, 3)                                 │    │
│  │     └─ 将 G_A 从 _Gwaiting 改为 _Grunnable          │    │
│  │         └─ 放入 P 的本地队列或全局队列              │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

这里的“直接拷贝”不是严格意义上的零拷贝：数据仍然要从发送方栈/内存拷贝到接收方目标地址。它的优化点是**跳过 channel 环形缓冲区**，避免“发送方 → buffer → 接收方”的二次中转。

### 4.4 从 GMP 视角串起来：`ch <- 1` 无接收方

```text
┌─────────────────────────────────────────────────────────────┐
│              无接收方发送：G、M、P、sudog 的联动              │
├─────────────────────────────────────────────────────────────┤
│  1. G_A 在 M0 + P0 上执行 ch <- 1                           │
│     G_A = _Grunning，M0.curg = G_A，P0 归 M0 使用             │
│                                                             │
│  2. runtime.chansend 发现 recvq 为空且无缓冲空间              │
│     创建 sudog，把 G_A、发送值地址、channel 关联起来          │
│                                                             │
│  3. sudog 进入 hchan.sendq                                   │
│     这表示“有一个发送方带着一个值在等接收方”                 │
│                                                             │
│  4. gopark 挂起 G_A                                          │
│     G_A: _Grunning → _Gwaiting                               │
│     M0 切回 g0，仍可使用 P0 执行调度代码                     │
│                                                             │
│  5. M0 调用 schedule 找其他 G                                │
│     优先从 P0.runnext / P0.runq / global / netpoll / steal 取 │
│                                                             │
│  6. 后续 G_B 执行 <-ch                                       │
│     从 sendq 取出 G_A 的 sudog，直接拷贝值，goready(G_A)      │
│                                                             │
│  7. G_A 重新进入可运行队列                                   │
│     G_A: _Gwaiting → _Grunnable，等待某个 M + P 再次执行      │
└─────────────────────────────────────────────────────────────┘
```

## 5. 系统调用与 Handoff

### 5.1 阻塞系统调用

当 G 执行阻塞系统调用（如文件 I/O）时：

```text
┌─────────────────────────────────────────────────────────────┐
│                  阻塞系统调用 Handoff                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  初始状态：                                                  │
│  M0 ──► G_syscall (执行 read 系统调用)                      │
│         │                                                   │
│         P0 (绑定 M0)                                        │
│         ├── 本地队列: [G1, G2, G3, ...]                      │
│         └── 绑定 M0                                         │
│                                                             │
│  G 进入系统调用：                                            │
│  M0 ──► G_syscall (阻塞在 read)                             │
│         │                                                   │
│         P0 (被 handoff)                                     │
│         ├── 本地队列: [G1, G2, G3, ...]                      │
│         └── 绑定到新 M1                                     │
│                                                             │
│  Handoff 完成：                                              │
│  M0 ──► G_syscall (阻塞中)                                  │
│         └── 等待系统调用返回                                │
│                                                             │
│  M1 ──► G1 (执行)                                           │
│         │                                                   │
│         P0 (绑定 M1)                                        │
│         ├── 本地队列: [G2, G3, ...]                          │
│         └── 绑定 M1                                         │
│                                                             │
│  系统调用返回：                                              │
│  M0 ──► G_syscall (系统调用完成)                            │
│         │                                                   │
│         G_syscall: _Gsyscall ──► _Grunnable                │
│         └── 放入全局队列或某个 P 的本地队列                 │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 非阻塞系统调用

对于网络 I/O 等非阻塞操作，Go 使用 netpoller：

```text
┌─────────────────────────────────────────────────────────────┐
│                    网络 I/O 处理流程                         │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  G 执行网络读取：                                            │
│  1. 设置 socket 为非阻塞模式                                │
│  2. 尝试 read                                                │
│  3. 如果 EAGAIN/EWOULDBLOCK：                               │
│     ├─ 将 G 注册到 netpoller                                │
│     ├─ G: _Grunning ──► _Gwaiting                          │
│     └─ M 继续调度其他 G                                     │
│                                                             │
│  数据到达时：                                                │
│  1. netpoller 检测到 socket 可读                            │
│  2. 将 G 从 _Gwaiting 改为 _Grunnable                      │
│  3. G 放入某个 P 的本地队列                                 │
│  4. G 被调度执行，read 返回数据                             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 6. 最佳实践

### 6.1 GOMAXPROCS 设置

```go

// - CPU 密集型任务：通常保持默认或按容器 CPU quota 设置
```

### 6.3 Channel 使用模式

```go
// 1. 超时控制
select {
case msg := <-ch:
    // 处理消息
case <-time.After(5 * time.Second):
    // 超时处理
}

// 2. 优雅退出
ctx, cancel := context.WithCancel(context.Background())
defer cancel()

go func() {
    for {
        select {
        case <-ctx.Done():
            return
        case msg := <-ch:
            // 处理消息
        }
    }
}()

// 3. 扇出扇入
func fanOut(input <-chan int, workers int) []<-chan int {
    channels := make([]<-chan int, workers)
    for i := 0; i < workers; i++ {
        channels[i] = worker(input)
    }
    return channels
}
```

## 8. 总结

GMP 模型是 Go 高并发的核心：

- **G (Goroutine)**：轻量级执行单元，初始栈 2KB
- **M (Machine)**：OS 线程，实际执行代码
- **P (Processor)**：逻辑处理器，管理本地运行队列

核心调度策略：
- 本地队列优先
- Work stealing 保证负载均衡
- Handoff 机制处理阻塞系统调用

Channel 阻塞的本质：
- `gopark` 将 G 挂起；对 channel 这类 runtime 可管理阻塞，M 通常继续持有 P 去调度其他 G
- `sudog` 携带 G、数据地址和 channel 关联，存入等待队列
- 接收方出现时直接拷贝数据（不经过 channel buffer），再通过 `goready` 唤醒发送方 G

最重要的边界：
- **channel 阻塞**：阻塞的是 G，M 不必阻塞，P 通常不需要 handoff
- **阻塞 syscall**：阻塞的是 M，P 需要被交给其他 M，避免 Go 代码并行度下降
- **netpoller**：把网络 I/O 等待交给事件轮询器，让 G 等待但不占住 M

这套设计使得 Go 能够支持百万级 goroutine 并发，同时保持极低的调度开销。
