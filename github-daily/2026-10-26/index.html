主题 A｜责任归属：agent 失败到底怪模型还是怪壳？

🧩 拆解 这批论文的技术内核是把「agent 能力」这个混合量强制分解。When Agents Fail: Model or Harness—Who's to Blame? 提出五个互补度量：有效完成率 VCR（不管对错，先看它能不能正常收尾并交出可评估的结果）、Model-Harness Fit（某个壳对某个模型的适配度）、Cross-Model Fit（壳的跨模型通用性）、Interaction Residuals（组件级汇总会掩盖的成对特异性强弱）、Token Load（含失败尝试的 token 开销）。 实验规模是这批论文里最大的：4 个通用壳（OpenCode / Codex CLI / Pi CLI / DeepAgents）× 4 个核心模型 + 2 个厂商原生模型-壳系统 × 6 个基准（上下文管理 / 工具使用 / 长上下文规划 / 多模态交互 / 产物交接），含压力条件共 111 个设置、52,168 条轨迹。 它和 10-24 期 Letta FrontierMemory 那份「五强排名」是竞争关系，不是互补：Letta 给的是单点排名，这篇给的是「排名随模型与基准漂移」的证据——同一对 model-harness，任务分和有效完成率可以指向不同赢家。结论里两个可核实的点：OpenCode 在跨模型表现上排第一；DeepSeek V4 Flash Preview 在共享四基准面板上保持稳定的高 Mean VCR。

💡 思路 为什么是现在？因为 10 月这半个月，行业刚刚接受「壳是独立变量」（10-18）、「壳可训练」（10-22）、「壳可排名」（10-24）。一旦壳被当成变量，下一个必然问题就是归因：模型升级了 5 分，是模型强了还是壳适配了？这篇给了可操作的答案——先测 VCR 再测正确率，先测交互残差再测总分。 它在这条主线上的位置是「测量学基础」。下一个突破点大概率不在「再排一次名」，而在两处：① 把 VCR 做成训练目标（模型学会「正常收尾」本身是一种能力）；② 把 Token Load 纳入性价比口径——目前所有榜单都按「答对率」排名，没有一家按「答对率 / 总 token（含失败重试）」排名，而后者才是生产环境的真实成本。

🗣️ 见解 明确立场：这是本期最该深读的一篇，也是我最愿意押注会被工程界立刻采用的一篇。 理由不是它结论惊人，而是它把一句正确的废话（「表现是模型和壳的联合函数」）变成了五个能算的数。相比之下，10-24 期我给 Letta 那份排名的评价是「有启发但样本太小」——这篇的 52,168 条轨迹把那个坑填了。 需要警惕的是它的样本仍局限于自家可跑的六基准，且 111 个设置里有相当一部分是「压力条件」而非生产分布；「OpenCode 跨模型第一」这个结论，在真实代码库 + 真实用户的分布上未必成立。 短期（1–4 周）内，我预期会看到「VCR」这个词出现在厂商的 eval 博客里；中期（1–3 月），「有效完成率 + token 成本」的双轴排名会取代单轴正确率，因为采购方开始按单任务成本算账。

主题 B｜规则的半衰期：写下来的经验会过期，而且过期的速度比失败慢

🧩 拆解 Lessons Outlive Their Failures: A Case Study of Rules for AI Coding Agents（2026-10-23）是一篇罕见的纵向个案：作者用一个纯 markdown 仓库当「个人 system of record」，让三个 AI agent 工具每天在共享规则集下编辑它，持续六周，建立了 118 条失败 → 修复 → 是否复发 的账本；又用 47 条已知过期陈述 + 20 条植入错误测试每月一次的「LLM 文档审计」；最后在隔离 git clone 里重放 5 个历史失败（有/无对应修复各 3 次）。 结果有四个硬数字：陈旧文档（drift）是最大失败类别，48/118（但其中 35 条是在同一个审计日被发现的）；单次审计能抓到约一半已知 drift（Claude Sonnet 5.5 均值 50%），且至少 93% 的发现是正确的；在 Sonnet 5.5 上，5 个重放任务完成了 4 个，其中 3 个失败根本没复发（有没有修复都一样）；唯一真正复发的是「过期计数」类失败，而它的机械检查在每次运行中都拦住了它。 同一主题还有一篇方法论文：CASE: Confusion-Aware Skill Evolution（2610.32481），把「情绪混淆」这种高度局部化的错误外化成稀疏、可自演化的 pair-specific EmotionSkills 库——不动权重，只长技能。

💡 思路 这两篇连起来指向一个正在成形的工程范式：规则不是提示词的附属品，是可版本化、可测试、可退休的资产。为什么是现在？因为 10-22 的《More Memory, Worse Agents》和 10-24 的 Raw-RAG 已经把「加法」这条路堵了一半；既然不能靠堆上下文，就只能靠筛选过的、带失效条件的规则。 这条线在主线上属于「harness 的运维学」——10-16 讲可测、10-18 讲可训练、10-22 讲可演化、10-24 讲可排名，今天讲的是「可退休」。下一个突破点在「规则的生命周期管理」：谁来判断一条 AGENTS.md 规则已经过期？这篇给的答案是重放（replay）——用历史失败当回归测试，跑不动了就退休。

🗣️ 见解 我给这篇很高的评价，但要把它的边界说死：单仓库、三工具、每条件三次运行，作者自己标注为 exploratory。 所以「93% 的发现是正确的」不能当成通用精度，「3/5 失败不复发」也不能当成「规则无用」——正确的读法是：大部分规则写下来之后，它要修的那个失败就不太会再出现了，于是规则开始空转；真正需要机械检查的是「计数/格式/引用」这类会自然漂移的东西。 这也解释了一个我一直困惑的现象：为什么 skill 生态里充满了「看起来正确但从不触发」的条款。因为规则的产出是失败驱动的，而规则的退役没人驱动。 短期（1–4 周）：会出现「AGENTS.md linter + 规则过期提醒」这类小工具；中期（1–3 月）：skill 仓库会开始带 last_validated 字段和重放脚本，这比再写十条规则有用得多。

主题 C｜真实世界的故障学：工具会抖，目标会藏

🧩 拆解 MCP-Injector: Tool-Calling LLM Agents Under Realistic MCP Faults（2610.32555）做了一件所有 benchmark 都回避的事：按真实故障分布往工具调用路径里注入故障。它的故障模型不是拍脑袋，而是从 1,774 个开源 MCP 仓库的 57,240 条 issue/PR 线程里挖出来的「故障模式 × 持续性」联合分布（永久 / 瞬时 / 间歇三档，可设种子复现）。 实验是 1,350 个格子的交叉设计：20B 与 120B 两个骨干 × 三种 agent 栈（自建多轮 plan-and-execute / OpenAI Agents SDK / LangChain）× 三种注入条件。两个结论足够刺眼：任务完成分从 8.08 掉到 3.23（-60%）；规模买不到容错——120B 在故障下保留的无故障得分比例并不更高（resilience-ratio 模型 p=0.96），完成率甚至更低（91.1% vs 95.6%，差 4.4 点，95% CI [-0.2, 9.3]）。真正拉开差距的是 agent 栈。 另一篇把「可见性」从假设变成任务：IGG: Interactive GUI Grounding under Visibility Constraints（2610.32536）——601 个任务、16 个可控 GUI 环境、7 类可见性约束（离屏、需状态变化后出现、悬停出现、被遮挡、延迟可操作），动作空间只有滚动/移动/拖拽/等待/点击。人类 94.6%，GPT-5.5 79.4%，最强开源 VLM 只有 31.6%。

💡 思路 这两篇合起来说明一件被忽略的事：agent 的能力评测一直在「理想工具」的假设下进行，而真实世界的第一性问题不是「会不会调」，是「调不通怎么办」和「看不见怎么办」。 在整条主线上，它们的位置是「把 benchmark 的假设逐条拆掉」——10-20 期拆的是「过程是否有效」，10-24 期拆的是「记忆是否越多越好」，今天拆的是「工具是否可靠」和「目标是否可见」。下一个突破点我猜在故障的语义层：现在的注入是协议层的（超时、5xx、连接断），而真实世界最贵的是语义层故障（工具返回了 200 但答案是错的），这一层目前没有基准。

🗣️ 见解 「规模买不到容错」这个结论，我会直接写进给团队的架构建议里。它和今天 HN 那条「10 年前的 CNN 打败前沿 LLM」是同一个反 scaling 叙事的两个面：一个说专用化在窄任务上更优，一个说规模在故障面前不提供鲁棒性。 但我要给 IGG 的数字泼一点冷水：31.6% 的开源 VLM 成绩很可能被「动作空间太窄」放大了难度（只有五种动作，没有键盘输入），而且 16 个环境规模偏小。它的价值不在排名，而在提出了「reveal 步骤」这个被所有 GUI benchmark 忽略的阶段——真实用户的界面里，一半的点击之前都要先「让它出现」。短期：MCP 客户端会开始内置重试/降级策略（现在多数是裸调）；中期：「故障注入」会成为 agent 平台的上线门禁，就像混沌工程之于微服务。

主题 D｜评测盲区：覆盖率是个会计科目，不是质量证明

🧩 拆解 Beyond Coverage and Mutation: A Blind-Spot Analysis of LLM-Generated Unit Tests（2610.32548）提出 BlindSpotEval：按 Arrange-Act-Assert 对齐的「义务（obligation）」评估，三个指标——边界值充分性、控制流充分性、Oracle 强度，外加执行可靠性。配套 ObligBench：895 个复杂 + 700 个低复杂度 Java 函数，带源码侧义务标注。跑了 4 个 LLM × 4 种提示策略共 14,320 个测试，最刺眼的数字是：错误断言占全部测试失败的 15.6%——也就是说，测试是绿的、覆盖率是涨的，但断言写错了。 LGMT（2610.32627）做的是「逻辑推理可靠性」的测试工具；PHYRD（2610.32575）则把物理推理基准做成「活的」：63 个 Reproduce + 43 个 Discover，五个模型在 Reproduce 上 49.21%–68.25%，闭卷 Discover 18.60%–74.42%；带工具能多做对几道，但概念错误与缺失论证依旧。附带一个很实用的发现：用 FormulaForest 造合成数据，能把 Qwen-35B-A3B 在 OpenAI 的 FrontierScience 上从 61% 提到 72%。

💡 思路 这一支的共同点：它们都在给「看起来很好」的指标装一个反例探测器。 覆盖率、变异分数、benchmark 总分，都是「投入量的会计」；而义务、盲区、Discover 题，才是「产出的审计」。 为什么是现在？因为 agent 已经能自己写测试、自己跑基准、自己报分数了——当被评测者开始生产评测，评测就必须换成不可被优化掉的形态。这与 10-22 期「不可复现的评测会被淘汰」、10-24 期「活 Web 评测需要时间快照」是同一条线的第三步：从「可复现」走到「不可刷分」。

🗣️ 见解 15.6% 的错误断言这个数字，比任何「LLM 写测试很强」的宣传都重要。它意味着 agent 写的测试里，每七个失败就有一个是测试自己错了——在 CI 里，这会训练团队「忽略红灯」，这是比漏测更严重的组织损害。 我对 PHYRD 的态度更谨慎：Discover 的 18.60%–74.42% 跨度太大，说明任务难度分布没有校准，这种基准容易被当成营销素材（挑高的那端引用）。但它「living benchmark」的定位是对的——理论物理的参考解会过期，基准必须能更新。短期：Java 生态会先受益（ObligBench 是 Java 的，直接可用）；中期：「测试的测试」会成为 CI 的标准一环，就像现在没人敢只看 coverage 数字一样。

主题 E｜规模化：一个模型五种预算，一个仓库十万个环境

🧩 拆解 Accordion: Elastic-Depth Inference via Fixed-Prefix Layer Looping（2610.32492）解决的是「同一模型要服务多种推理预算」的部署成本问题：用 MoE + 固定前缀层循环，让五种推理预算共享一套参数，每个预算走一条预定义执行路径，最小预算保留未循环的原模型；预训练时每个 micro-batch 只采一个预算做 next-token 预测，不加跨预算一致性目标，SFT/RL 阶段再用参数组融合与 budget-matched 多教师来保住各档能力。 POSEIDON（2610.32448）解决的是「科学 agent 没有训练环境」：从科学代码仓库自动生成可执行、可验证的环境，把科学工作流拆成四类任务——Reproduction / Subflow / Completion / Correction，配一个递归改进回路把失败候选救回来。同样的仓库预算下，产出的环境数量约为前作的 10 倍；据此构建的 Pearl 集合含 97,659 个可执行可验证环境。

💡 思路 两篇一个向内（模型内部的算力弹性），一个向外（训练数据的环境弹性），但命题相同：「一个固定配置」的时代结束了，系统必须能在预算与环境两个维度上伸缩。 为什么是现在？因为价格战已经把「单位 token 毛利」压到极限（见模块 1 第 2 条），而 agent 训练又需要海量可验证环境。成本压力从两头挤：推理要能按预算降档，训练要能按仓库放大。 下一个突破点：预算档位与 harness 的联合调度——现在 Accordion 假设「预算由部署方选」，实际生产中预算应该由 agent 根据任务不确定性动态选。

🗣️ 见解 Accordion 是漂亮的工程，但它的评估前提是「五档预算的性能都保住了」——摘要只给了方法，没给跨档的具体退化曲线，所以我把它列为「值得跟踪，暂不下结论」。真正让我兴奋的是 POSEIDON 的 97,659 这个数字：它把「环境」从手工活变成了可编译产物。 这解释了一个长期困惑：为什么 agent 在 SWE 类任务上进步快、在科研任务上慢？不是模型不行，是可验证环境的供给不足——代码仓库天然带测试，科学代码不带。谁把「验证信号」工业化，谁就拿到下一轮的训练数据入口。 这也是我对 2027 年最重要的一个判断：环境的产能会成为 agent 公司的核心资产，比权重更稀缺。

2.3 HF 模型 / 数据集推荐（上期未覆盖项，逐条标注）

口径：HF Daily Papers 2026-10-23 批次共 49 篇，票数最高 8 篇中 6 篇已在 10-24 期覆盖。以下为上期未出现、且票数靠前的三项，均来自同一批次（不是今天新发）。

① Editing Images into Reusable Layers via Compositional Edit-Prior Distillation ｜HF 论文页 · 184 票（该批次第 2 高票） 把「一次编辑的结果」蒸馏成可复用的图层（compositional edit-prior），而不是一张扁平输出图。定位是「图像编辑的可组合性」——你要的不是新图，是能再次编辑的结构。与当前主流「一句话改图」的差异在于：它把编辑的中间表示当一等公民，这对设计工具（Figma 类）比对手机构图 app 更有意义。为什么放这里：它与今天 Trending 的两个设计 skill（hallmark / impeccable）形成奇妙的互补——一个在约束生成的美学，一个在保留编辑的自由度。

4.1 Java & Spring 生态 —— JDK 28 的最后一块拼图：AOT 代码进缓存

① JEP targeted to JDK 28: 544: Ahead-of-Time Code Compilation — inside.java，2026-10-25（JEP 本体：openjdk.org/jeps/544，Created 2024-06-30 / Updated 2026-10-14，Owner John Rose，Status Integrated，Release 28） 这是本期 Java 侧唯一的新增，但它分量足够：JDK 28 的 AOT 故事从「类加载与链接」走到了「本地代码」。

它到底做了什么：把 training run（训练运行） 里由 C1/C2 编译出的优化后本地代码存进 AOT cache；生产运行时，当某个方法需要优化代码，如果缓存里有匹配的 AOT code 就立刻用，没有/不兼容/被 deoptimize 就静默回落到解释器与 JIT。

# 训练运行（生成 AOT cache，含 AOT code）
java -XX:AOTCacheOutput=app.aot -XX:AOTMode=record ...  # 具体参数以 JEP 544 正文为准
# 生产运行（直接吃缓存）
java -XX:AOTCache=app.aot -jar app.jar

JEP 明确的目标与非目标，值得逐条看：

  • 目标：更快到达峰值性能；工作负载变化时能动态重新生成（AOT + JIT 并存，这是它和 GraalVM native-image 的根本区别）；应用/库/框架零改动；HotSpot 配置零改动（除了请求使用 AOT cache）；继续支持 Serial / Parallel / G1 / Shenandoah / ZGC；不引入新工作流（复用 JEP 483 的 AOT cache 创建流程）；AOT→JIT 的切换对应用不可见；支持 AArch64 与 x64。
  • 非目标：不提供「纯 AOT 模式」；不支持交叉编译（训练与生产的 CPU 架构与特性集必须一致）；不承诺覆盖所有架构。
  • 技术前提：AOT code 与 JIT code 由同一套编译器（C1/C2）产出，因此完全互操作。

为什么重要（三条）：

  1. 这是 Leyden 的收口。10-24 期我们写过 JEP 483（AOT 类加载与链接）、JEP 515（AOT 方法剖析）、JEP 545（ZGC 更快启动预热）、JEP 546（自适应堆大小）。544 把最后一块——编译产物——补上了，JDK 28 因此第一次拥有完整的「启动即接近峰值」路径。
  2. 它直接打在 agent 沙箱与 serverless 的痛点上。本期模块 4.2 讲 K8s 的 agent warm pool：agent 要在毫秒级「复活」，而 JVM 的传统弱点是冷启动 + 预热。AOT code 把「跑几千次才 JIT 出来」变成「第一次就拿到优化代码」——这不是性能优化，这是把 JVM 塞进短生命周期场景的入场券。
  3. 它的保守值得称赞。不做纯 AOT、不支持交叉编译、必须同 CPU 特性集——这三条限制把「AOT cache 不可移植」写在了明面上，避免了「构建机与生产机不一致导致神秘性能回归」这类最贵的坑。对比 GraalVM native-image 的封闭世界假设，HotSpot 选择的是渐进式、可回落、与 JIT 共存的路线。

与前 3 期的延续：10-24 期判断「JDK 28 的四张牌打的是容器化/短生命周期场景」→ 本期 ✅ 收口：483/515/544/545/546 五张牌合起来，才是「Java 在 agent 时代的位置」这个问题的完整答案。⏸ Spring 侧：spring.io/blog.atom 最新四条仍是 10-23 的 Spring AI 2.1.0-RC1/2.0.2 与 Boot 4.0.9 / 4.1.2 / 4.2.0-RC1，上期已逐条拆过，窗口内无新增。

4.2 云原生 Infra —— 三个真实矛盾：调度打架、agent 要暖池、安全 agent 的分数怎么读

① Why Kubernetes autoscalers keep fighting each other (and why the solution must be autonomous) — The New Stack（CNCF 赞助内容），2026-10-24 文章开篇那个场景几乎是所有平台团队的日常：一个 checkout-api，Helm 写 replicas: 3 / cpu: 1000m / memory: 2Gi，而活集群里 HPA 按 CPU 扩到 11 个副本、VPA 说它过度配置建议降到 cpu: 350m / memory: 3.1Gi、KEDA 因为 Kafka 积压要 24 个副本、Karpenter 按「声明 requests 而不是实际用量」新开了两台节点。五个来源，五个互相矛盾的答案。 它把根因讲得很清楚：Unix 哲学在这里失效。grep | awk 能组合，是因为它们处理不可变数据流、顺序执行；而 HPA/VPA/KEDA/Karpenter/ArgoCD 并发地对同一批 API 字段（.spec.replicas、.resources.requests、节点池）做写操作，每个控制器都假设自己独占决定权。 四个具体碰撞里，第一个最值得抄进故障手册——「分母坍塌」（HPA vs VPA）：HPA 按「实际用量 / 声明 requests」算利用率，VPA 为了省成本下调 requests，分母变小 → 同样的流量把百分比顶过阈值 → HPA 激进扩容 → 每 pod 用量下降 → VPA 继续下调 → 进入「微小容器舰队」的死亡螺旋。第二个是多写者竞态（KEDA 与 HPA 同时打同一个 /scale 子资源）。 为什么重要：这是「为可压缩资源设计的调度模型，遇上不可压缩的 AI 负载」的直接后果。10-24 期我们写过「GPU 闲着但任务在排队」，今天这篇给了机制层解释：不是 K8s 不会调度，是五个控制器在抢同一支笔。

② Is Kubernetes ready for AI agents? — The New Stack（CNCF 赞助内容，作者 Dan Ciruli，Nutanix 云原生业务负责人），2026-10-25 核心问题一句话：「怎么在不付每次新建环境启动成本的前提下，拿到全新环境的隔离性？」 它给出的答案是一个正在成形的抽象：agent substrate（agent 基底）+ warm pool（暖池）。agent 不被完全销毁，而是**「处于暂停动画状态」，需要时毫秒级复活**，而不是从深睡里花几秒唤醒。文章的判断是：第一代 K8s 不支持有状态应用，社区花了好几年才找到正确的抽象（StatefulSet/Operator）；agentic 负载正在重复这个过程，「社区仍在寻找运行新一代 agent 负载的最佳抽象层」。 为什么重要 + 必须打的折扣：方向上它和 10-24 期「GPU 调度与 autoscaler 同步」完全一致，而且「暖池」这个词抓住了 agent 负载的本质——agent 的闲置不是空闲，是待命。但这是 CNCF 赞助内容、作者来自平台厂商，结尾自然落到「前瞻性的平台厂商正在构建 guardrails/sandboxing/monitoring/agentic substrate」。技术判断可用，产品结论要打折。

1）A hash-only rollup: OP Stack L2 accounts as Lamport-style hash chains, no ECDSA inside the L2 — ethresear.ch，2026-10-24（作者自述是 bb84 创始人，链上已上线） 这是本期最硬的一篇，也是「后量子」讨论里少见的「已经在主网跑」的样本。 它做的事一句话能说清：L2 里没有签名。

机制逐层拆：

  • 账户 = 哈希链的端点。s_0 = keccak256("OP_OTA_SPEND_v1" ‖ spend_sk ‖ r)，然后 s_k = keccak256(s_{k-1})，默认 N = 1000；公开承诺 C = s_N，地址 = trunc20(keccak256("OP_HASH_ADDR_v1" ‖ C))。花钱就是揭示下一个原像（Lamport 一次性签名的变体）。
  • 问题随之而来：揭示原像等于公开它，任何人都能抢跑。解法是先承诺后揭示：新增两种 EIP-2718 交易类型（0x7C HashCommitTx / 另一型为 reveal），commit 步骤把每个原像绑定到唯一一笔交易，在原像公开之前完成绑定。预部署 NullifierTree（0x4200…0042）为每个地址存 lastReveal（初始 = C）、chainDepth（初始 = N）与已花费 nullifier 集合。
  • 密码学假设：L2 内部只剩 keccak-256 的原像抗性，Grover 之下约 2^128 工作量，作者称无已知量子算法更优。ECDSA 仍出现在 L1 边界，且系统还有其它信任假设（作者自己列了，并明确请人「指出它在哪里坏掉」）。
  • 实测状态：OP Stack rollup，chain ID 42069000，2026-09-30 起在主网运行。 为什么重要：以太坊的后量子讨论长期停留在「账户抽象怎么换签名方案」（10-22 期我们写过 ERC-8403 的 PQ key），而这篇走了一条更激进的路——把签名从 L2 里彻底删掉，用一次性哈希链 + nullifier 集合替代。代价很明显：N=1000 意味着账户有寿命（用完要换链）、每次花费都要两次交易（commit/reveal）、状态增长与 nullifier 存储都是新负担。它是「可用性换后量子」的极端点，值得读是因为它把权衡摆在了明面上。

2）〔上期已覆盖，仍在被讨论〕Reveal optionality in encrypted mempools — 2026-10-22 和上面那篇构成一个漂亮的对称：加密 mempool 的核心矛盾是「谁有权选择何时揭示」，而哈希链 rollup 把揭示做成了协议强制的两步。 这篇的结论「把期权从发送者手里拿走，它只是转移到委员会成员手里」在本期依然成立——哈希链方案同样把权力转移给了「谁先看到 commit」的人（排序者）。这是我读第 1 篇时最想问作者的问题。

3）〔上期已覆盖〕Paranoid EIP-8288: heterogeneous recursion with an authenticated class bank — 2026-10-22 「证明系统的参数也进共识」——class 集合是公共参数，升级证明后端 = 一次协议治理动作。这条线本期没有新进展，但它是理解 L2 证明市场的前提。

4）结构性事实一：L2 正在收缩，而不是扩张 二手来源（Phemex 行业综述、RZLT 综述，均未在链上复核）给出的时间线：Blast 于 2026-10-02 宣布逐步关停，Abstract 于 10-06 公布关闭计划；L2BEAT 追踪 73 个活跃 rollup、约 480 亿美元，其中两条链占 77% 的价值。 为什么重要：如果这两个日期成立，那么「发一条 L2」的边际价值已经在归零——这正是第 1 篇那种「极小众但机制上有新意」的实验能获得关注的原因：在通用 L2 的红海里，只有机制层面的差异化（后量子、无签名、可验证排序）还有讨论价值。

🎯 6. 今日 AI 学习知识点

主推荐：约束栈（Constraint Stack）—— 把「别这样」分成三层，只有一层该写成代码

一、是什么 今天 Trending 榜上两个设计 skill（hallmark、impeccable）和一篇论文（Lessons Outlive Their Failures）不约而同地在做同一件事：给「约束」分层。把它抽象出来，就是一个可复用的四层结构：

层 形态 谁来执行 违反的后果 今天看到的实例
L0 硬门禁（Floor） 类型系统、单测、linter、CI 门 确定性代码 构建失败，不进主干 hallmark 的 Floor 门（对比度、焦点、reduced-motion、编造事实、手机布局崩坏）「永不放行」
L1 默认反射（Reflex） 规则文件里的默认值（AGENTS.md / SKILL.md） 模型，但允许有理由地推翻并留痕 需要写理由，reviewer 可能驳回 hallmark 的 Reflex gates；论文里的 rule ledger
L2 检测器（Detector） 确定性检查脚本 代码，但事后运行 警告/打回重做 impeccable 的 62 条确定性检测规则（Inter 用滥、紫蓝渐变、卡片套卡片、彩色底上灰字…）
L3 建议（Advisory） 文档、风格指南、口头约定 人 无 大多数团队的「代码规范.md」

关键洞察：今天两个仓库最聪明的设计，是把「AI 味」从审美问题变成了 L2 的确定性问题。 hallmark 的 sloplint 检查的不是「好不好看」，而是可枚举的机器痕迹：每个标题上方的小标眉（eyebrow）、字距放大的大写标签、标题里一个彩色词、满页空框或纯图、hero 撑不满首屏、每页末尾都塞邮件订阅、表单点了「谢谢」但什么都没发出去。impeccable 走同一条路，只是规模更大（62 条 + 24 条命令 + 浏览器内实时迭代）。审美无法被规则化，但「审美的失败模式」可以被规则化。

二、为什么是现在最重要 三个信号在同一周对齐：

  1. 模型能力的边际收益在收窄。今天 HN 那条「10 年前 CNN 62% vs 前沿 LLM 42%」（链接）和论文「规模买不到容错」（MCP-Injector，8.08→3.23，120B 不比 20B 更能扛）说的是同一件事：继续加参数不再自动换成可靠性。
  2. 规则一旦写进 prompt，就会漂移。论文的账本给了最硬的数字：118 次失败里 48 次是「陈旧文档」，其中 35 次集中在同一个审计日被发现；单次审计只抓到约一半已知 drift（Sonnet 5.5 均值 50%），但发现的正确率 ≥93%。也就是说：模型能准确地告诉你「这条规则过期了」，但它不会主动去查。
  3. 规则正在变成可分发资产（10-24 期：Agent Skills 进 AAIF）。资产就需要版本、审计、报废——这正是约束栈要解决的问题。

三、趋势

  • 短期（1–4 周）：skill 仓库开始自带 linter（hallmark 已经把 sloplint 打包进安装流程）；「62 条检测规则」这类可数的确定性资产会成为 skill 的卖点。
  • 中期（1–3 月）：AGENTS.md 会出现类似 last_validated 的元数据，配套重放测试（用历史失败当回归集）。论文已经证明这条路可行：5 个重放任务里 3 个「有没有修复都不再复发」，唯一复发的那类被机械检查 100% 拦住。
  • 长期：「约束的约束」会成为一门工程——谁来审规则、规则之间是否冲突（例如「所有页面都要有 CTA」与「每页末尾不要订阅框」）、规则失效后如何回收。

四、延伸学习

  1. 先读 Lessons Outlive Their Failures（看它的账本结构：失败 → 修复 → 是否复发 → 重放），再读 When Agents Fail（看「有效完成率」为什么必须和正确率分开）。
  2. 然后去看两个仓库的规则文件本身（不是 README，是 skill 目录里的 markdown + 检测脚本）：hallmark、impeccable。
  3. 最后做一件小事：把你自己的 AGENTS.md 里超过 30 天没有被触发过的规则标出来——那就是你的 drift 起点。

Drew Breunig 在 The State of Context Engineering（10-24）里给了一句可以直接当决策规则用的话：「我们的工作是判断什么时候该确定性（写进代码），什么时候该概率性（交给模型）。」 配套的历史叙事值得记：2024 年底「RAG is dead，窗口够大就塞下一切」→ 百万上下文落地后发现注意力与成本双重不可行→ 回到「选择性供给 + 主动遗忘」。HN 上最实用的一条反例是：别人家的 harness 和你自建的 harness 会互相干扰，最后「什么都不配」反而更好——这是「约束栈」的负向验证：约束不是越多越好，冲突的约束等于没有约束。

📄 1）When Agents Fail: Model or Harness—Who's to Blame?（2610.32483）

核心贡献：把 agent 评测从「单点分数」改成「model × harness 的交互矩阵」，给出五个度量（VCR / Model-Harness Fit / Cross-Model Fit / Interaction Residuals / Token Load），并在 111 个设置、52,168 条轨迹上验证「排名会随模型与基准漂移」。 为什么重要：它解决了 10-24 期那份 harness 排名遗留的方法论问题——排名不是错的，是缺了一个「对谁而言」的限定词。两个可核实结论：OpenCode 跨模型第一；DeepSeek V4 Flash Preview 在共享四基准面板上保持稳定高 Mean VCR。 延伸阅读：TNS 对 Letta FrontierMemory 的报道（10-21，对照其 15 任务/单次运行的局限）。

📄 2）Lessons Outlive Their Failures: A Case Study of Rules for AI Coding Agents（2610.32578）

核心贡献：六周、一个仓库、三个 agent 工具、118 条失败账本的纵向个案；用 47 条已知过期 + 20 条植入错误测审计精度；用隔离 git clone 重放 5 个历史失败。 为什么重要：它是目前少有的、关于「规则会过期」的实证。四个数字请记住：drift 48/118（最大类）、审计召回约 50%、精确率 ≥93%、3/5 失败不再复发、唯一复发的那类被机械检查 100% 拦住。作者自标 exploratory（单仓库、三次运行），结论方向可信，精度数字不可外推。 延伸阅读：More Memory, Worse Agents（10-22，记忆的加法反噬）。

📄 3）MCP-Injector: Tool-Calling LLM Agents Under Realistic MCP Faults — Scale Does Not Purchase Fault Tolerance（2610.32555）

核心贡献：从 1,774 个开源 MCP 仓库的 57,240 条 issue/PR 线程里挖出真实故障分布，做成协议感知、可复现种子的故障注入中间件；在 1,350 个格子（20B/120B × 三种 agent 栈 × 三种注入条件）里测韧性。 为什么重要：任务完成分 8.08 → 3.23（-60%）；120B 不比 20B 更抗故障（resilience ratio p=0.96，故障下完成率 91.1% vs 95.6%，95% CI [-0.2, 9.3]）；真正决定韧性的是 agent 栈。这是一篇会改变采购标准的论文：能力榜单一句话都不能说明生产可靠性。 延伸阅读：Good Judgment, Bad Advice（10-22，控制器加成本不加收益）。

📄 4）CASE: Confusion-Aware Skill Evolution for Frozen Multimodal Emotion Models（2610.32481）

核心贡献：观察到「情绪混淆高度局部化」（只在语义相邻的情绪对之间发生），于是不动权重，维护一个稀疏、自演化的 pair-specific EmotionSkills 库，把情感专长从参数里外置出来。 为什么重要：它是「技能作为补丁」的最干净样本——10-22 期《Harness Self-Evolution》讲壳的演化，这篇讲技能库按错误对精准生长，而不是全参数微调。对工业界的启示：你的 agent 犯错是局部聚集的，先聚类错误对，再写技能，比再去微调一次便宜得多。 延伸阅读：Lessons Outlive Their Failures（技能会过期，所以需要退休机制）。

📄 5）Accordion: Elastic-Depth Inference via Fixed-Prefix Layer Looping（2610.32492）

核心贡献：用 MoE + 固定前缀层循环让一个模型支持五种推理预算，每个预算走预定义执行路径，最小预算保留未循环的原始模型；预训练每 micro-batch 只采一个预算，不额外加跨预算一致性损失；SFT/RL 阶段用参数组融合与 budget-matched 多教师保住各档能力。 为什么重要：价格战（模块 1 第 2 条）之后，「一个模型服务多种预算」直接决定毛利。它的路线与「训练多个小模型」相反：参数复用，路径分化。 边界：摘要只给方法不给跨档退化曲线，「五档都保住性能」目前是作者主张，需要看正文实验再下结论。 延伸阅读：RouteWeaver（路由与执行模式统一决策）。

📄 6）POSEIDON: Scaling Training Environments for Scientific Agents from Code Repositories（2610.32448）

核心贡献：从科学代码仓库自动生成可执行、可验证的训练环境，把工作流拆成 Reproduction / Subflow / Completion / Correction 四类任务，配递归改进回路回收失败候选；同样仓库预算下环境数量约为前作 10 倍，据此构建的 Pearl 含 97,659 个可执行可验证环境。 为什么重要：agent 在 SWE 类任务上跑得快，是因为代码仓库天然带测试；科学代码不带，所以科研 agent 缺「验证信号」。这篇把环境的产能问题变成工程问题。我的判断：环境的产能会变成 agent 公司的核心资产，比权重更稀缺。 延伸阅读：SCI-AGENT-EXAM、PHYRD（后者用 FormulaForest 合成数据把 Qwen-35B-A3B 在 FrontierScience 上从 61% 提到 72%）。

📄 7）IGG: A Benchmark for Interactive GUI Grounding under Visibility Constraints（2610.32536）

核心贡献：把 GUI grounding 的隐含假设（目标已经在截图里可见）打破，要求 agent 先通过交互让目标可见，再点击；601 任务 / 16 环境 / 7 类可见性约束，动作空间仅滚动、移动、拖拽、等待、点击。 为什么重要：人类 94.6%、GPT-5.5 79.4%、最强开源 VLM 31.6%——「reveal 步骤」是目前 GUI agent 最大的能力断层，而它恰恰是真实界面的常态（折叠菜单、悬停出现、懒加载、延迟可点击）。 边界：16 个环境规模偏小，动作空间窄（无键盘输入）可能放大难度，排名不要外推，但「reveal 是独立能力」这个提法会被后续基准继承。 延伸阅读：WaitLens（工业 GUI 测试 agent 的自适应等待）。

🧠 Paper 深度总结

第一段：这一批论文的共同姿态是「拆假设」。 拆「模型和壳可以分开评」（32483）、拆「写下来的规则一直有效」（32578）、拆「工具会正常响应」（32555）、拆「目标已经在屏幕上」（32536）、拆「覆盖率等于质量」（32548）、拆「一个模型只能有一种算力配置」（32492）。六篇论文，六个被默认了两年、今天被证伪的假设。 这不是巧合：当能力增长放缓，学术界的注意力自然转向「系统在哪里漏水」。

第二段：漏得最厉害的地方是「验证」，不是「生成」。 把数字并排放：MCP 故障下完成分掉 60%；LLM 写的测试里 15.6% 的失败是断言自己错了；规则审计能准确判断（93%）但只覆盖一半（50%）；AI 补丁能修掉一个真 bug（89%）但只有 37.8% 修的是那个 bug；GUI agent 能点（79.4%）但常常点不到该点的东西（人类 94.6%）。生成侧的曲线还在涨，验证侧的曲线几乎没动。 这就是为什么今天 GitHub 榜上是两个「给 agent 装审美门禁」的仓库，而不是又一个模型。

第三段：下一轮的竞争点在「可测量性」。 32483 的 VCR、32548 的义务覆盖、32578 的重放测试、32555 的故障注入，都是同一类东西——把「我觉得它行」换成「它在什么条件下不行」。这也解释了为什么 10-24 期的 harness 排名会引起那么大反应：它第一次把「壳」放上了秤，而今天的这批论文在说：秤本身需要校准。

🔢 今日算法知识点（阿楠专项）— 尾部放大与对冲请求（Hedged Requests）

附注：由每日算法知识点 cron 自动追加（08:15）。本条为 22:00 合写日记补记 —— 08:15 该 job 运行时今日日报尚未落盘（日报 09:21 才完成），按幂等规则跳过追加，今日模块缺失；此处按同一份推荐原文补入，来源群消息 message_id 9586，内容未改写。

核心要点

  • 平均响应时间会骗人。 一个请求要打 100 个分片，单片 p99 是 1s 听着还行，但「100 片里至少有一片超过 1s」的概率是 1 - 0.99^100 ≈ 63%，整体 p99 就被拖到 2s 以上。这就是尾部放大：用户体感由最慢的那一片决定，不由平均决定。所以扩容对 p50 很友好，对 p99 基本没用。
  • 对冲不是重试。 主请求发出去，等到 p95 还没回来，就往另一个副本再发一份一模一样的，谁先回用谁，另一个直接 cancel。重试是等失败了再发，对冲是还没失败就先发。
  • 代价很划算：多花 5%～10% 的请求量，p99 能掉一个量级。gRPC 里这是内建策略，Java 端 enableHedging + hedgingDelay 直接设成观测到的 p95 就行。

示例

ctx, cancel := context.WithCancel(ctx)
defer cancel()                      // 返回时顺手掐掉还在跑的输家

ch := make(chan res, 2)
go func() { ch <- get(ctx, replicaA) }()

select {
case r := <-ch:
    return r.v, r.err
case <-time.After(p95):             // 慢得不像话了
    go func() { ch <- get(ctx, replicaB) }()
    r := <-ch                       // 谁先到用谁
    return r.v, r.err
}

两个坑

  • 只对幂等读天然成立；写请求要对冲必须先有幂等键，否则就是重复扣款。
  • 副本已经过载时对冲会火上浇油 —— 必须有「最多发 N 份」的上限加重限流，不然慢请求会把整个集群压死。

小建议 / 后续阅读

  • 读 Dean & Barroso 的 The Tail at Scale（2013）：里面还有更优雅的变体 tied requests —— 不发第二份请求，而是让两份在副本队列里排队，谁先排到谁执行，服务端主动取消另一份。代价比对冲更低，Google 内部用得挺多。
  • 落地第一步不是加对冲，而是先把 p95/p99 分开观测：p50 好的系统经常 p99 已经烂了，只是没人量。
